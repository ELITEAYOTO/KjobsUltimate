# KjobsUltimate V3.15 — Persistence Performance

## Objectif

Supprimer le modèle historique :

```text
progression quête
  -> création d'une task Bukkit async
  -> 1 connexion/lock DB
  -> 1 écriture SQL
```

V3.15 utilise :

```text
QuestManager.progress()
        ↓
QuestWriteBuffer
        ↓
QuestWriteQueue
(UUID + questId)
        ↓
coalescing RAM
        ↓ toutes les 40 ticks par défaut
max 500 snapshots
        ↓
1 task async
        ↓
1 transaction DB
        ↓
PreparedStatement batch
```

## Exemple

Un joueur fait progresser `mineur_stone_1` 100 fois pendant la fenêtre de
2 secondes.

Avant V3.15 :

```text
100 signaux
100 tasks async
~100 séquences SQL
```

V3.15 :

```text
100 signaux
1 paire pending joueur/quête
1 snapshot au flush
1 batch transaction
```

Le dernier état RAM est conservé : la progression intermédiaire n'a aucune
raison d'être persistée 100 fois.

## SQLite

Le correctif portable V3.14.1 reste utilisé :

- `INSERT OR IGNORE`
- `UPDATE MAX/MIN`

V3.15 prépare ces deux statements une seule fois par batch, utilise
`addBatch()/executeBatch()` et effectue tout le lot dans une transaction.

## MySQL

- une connexion Hikari par lot ;
- une transaction par lot ;
- un PreparedStatement `ON DUPLICATE KEY UPDATE` réutilisé ;
- `rewriteBatchedStatements=true` est déjà présent dans l'URL MySQL.

## Sécurité monotone

Une écriture ancienne ne peut pas faire régresser :

- `progress`
- `completed`
- `claimed`
- `completed_at`

En cas d'échec d'une transaction, le lot entier est rollback puis remis dans
la queue si `retry_failed: true`.

## Reset administratif

Un reset est différent : il doit pouvoir remettre une progression à zéro.

V3.15 utilise donc une barrière par `(UUID, questId)` :

1. bloque la clé ;
2. supprime l'ancien pending ;
3. attend la fin d'un batch déjà en vol ;
4. applique le reset SQL ;
5. débloque la clé ;
6. une nouvelle progression survenue après le reset peut ensuite être flushée.

Une vieille progression ne peut donc pas réapparaître derrière un reset.

## Quit / shutdown

Au quit, `PlayerDataManager.saveAndUnload()` continue d'effectuer une
sauvegarde complète du joueur. Le buffer peut en plus demander un flush
prioritaire.

Au shutdown :

1. autosave périodique stoppé ;
2. attente du batch déjà en vol ;
3. drain synchrone du QuestWriteBuffer ;
4. `PlayerDataManager.saveAll()` ;
5. fermeture DatabaseManager.

## Fenêtre de crash

Avec `flush_interval_ticks: 40`, une progression ordinaire peut rester environ
2 secondes uniquement en RAM en cas de crash brutal de la JVM/machine.

Les complétions de quête utilisent par défaut un flush immédiat.

## Mémoire

La queue est indexée par paire distincte `(joueur, quête)`, pas par action.

Exemple théorique : 700 joueurs avec 3 quêtes modifiées dans la fenêtre :

```text
~2100 pending maximum
```

et non le nombre de blocs cassés pendant ces 2 secondes.

## Diagnostics

En mettant temporairement :

```yaml
debug_quest: true
```

un batch réussi peut afficher :

```text
[QuestWriteBuffer] batch=42, pending=0, coalesced=94.8%, time=3ms
```

`/kjobs perf` global est volontairement réservé à la phase diagnostics finale.
