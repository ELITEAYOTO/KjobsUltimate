# KjobsUltimate V3.13 — Action Accounting / Correctness

## Objectif

Une action réelle possède une quantité unique `units`.

Cette quantité est utilisée pour :

- XP
- money
- HUD
- quête

Il ne doit plus être possible d'avoir :

- XP x1 mais quête x4
- XP x2 mais quête x1
- money calculé sur une autre quantité

## Farmer

### Blé 1.8.8

Le bloc Bukkit 1.8.8 est `CROPS`.

`WHEAT` reste accepté uniquement comme alias de compatibilité pour un ancien
`farmer.yml`.

### Canne à sucre / cactus

Exemple :

```text
Y66 SUGAR_CANE
Y65 SUGAR_CANE <- cassé
Y64 SUGAR_CANE
```

Résultat :

```text
units = 2
```

Si `SUGAR_CANE_BLOCK.xp = 5` :

```text
XP brute = 10
quête HARVEST = +2
money = money_unitaire x2
HUD = XP réellement attribuée
```

Le bloc inférieur n'est jamais compté.

## Craft vanilla

`count_mode: CRAFTS` est le défaut.

Un shift-click est estimé selon :

1. le plus petit stack d'ingrédient présent dans la matrice ;
2. la place disponible pour le résultat dans l'inventaire.

`RESULT_ITEMS` multiplie ensuite le nombre d'exécutions par la quantité de
résultat de la recette.

## Kcraft

Résolution :

```text
KCRAFT:<craftId>
       |
       +-- trouvé -> action exacte
       |
       +-- absent -> fallback Material résultat
```

`allow_forced: false` est le défaut.

Un `KcraftPostCraftEvent.wasForced() == true` ne donne donc rien sauf
autorisation explicite.

## Quêtes et Kcraft

V3.13 envoie un seul signal de quête par action Kcraft :

```text
type   = CRAFT
target = Material résultat
amount = units
```

Le `craftId` sert à sélectionner la récompense Artisan exacte, mais n'envoie
pas un deuxième `QuestManager.progress()`.

C'est volontaire : deux signaux successifs pour une même action physique
pourraient terminer une étape puis faire progresser immédiatement l'étape
suivante de la même chaîne.

Une future extension de quête par `craftId` devra utiliser un traitement batch
atomique côté QuestManager.
