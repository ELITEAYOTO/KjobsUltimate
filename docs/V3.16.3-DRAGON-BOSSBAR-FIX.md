# KjobsUltimate V3.16.3 — BossBar Dragon 1.8

## Statut

- Correctif source : terminé.
- Tests automatisés : 48/48 réussis.
- Validation visuelle Minecraft 1.8.9 / Lunar / OptiFine : à effectuer sur le
  serveur de développement avant publication.

## Symptômes reproduits

Avec l'ancien placement relatif :

```yaml
dragon_distance: 28.0
dragon_vertical_offset: -38.0
```

le modèle du Dragon apparaissait quand le joueur était assez haut. En
augmentant fortement le décalage négatif, l'entité pouvait au contraire passer
sous la limite client et la bossbar disparaissait.

## Cause exacte

La bossbar Minecraft 1.8 est dérivée du rendu d'une entité boss. KjobsUltimate
n'ajoute aucune vraie entité au monde : il construit un Dragon NMS et l'envoie
uniquement au joueur avec des paquets de spawn, métadonnées, téléportation et
destruction.

Le rendu du Dragon 1.8 ne masque pas son modèle grâce au seul drapeau
d'invisibilité. Ce drapeau reste envoyé pour une sémantique cohérente, mais il
ne constitue pas la protection visuelle.

Le placement relatif était donc intrinsèquement ambigu :

- joueur haut : le Dragon restait dans le monde visible ;
- joueur bas : un grand décalage pouvait placer l'entité sous `Y=-64`, où le
  client la supprime ;
- une même valeur ne pouvait pas garantir les deux invariants.

## Vérification du client 1.8.9

Le bytecode Vanilla/OptiFine 1.8.9 a été vérifié sur les chemins réellement
utilisés par le client :

- `RenderDragon` actualise `BossStatus` au début de son rendu ;
- son rendu du modèle contourne le test d'invisibilité générique, ce qui
  explique le Dragon visible malgré le bit `0x20` du DataWatcher ;
- le constructeur de `EntityDragon` fixe `ignoreFrustumCheck=true` ;
- sa taille `16 x 8 x 16` produit une portée de rendu d'environ `853,33`
  blocs avec la formule vanilla de `Entity.isInRangeToRender3d` ;
- `Entity.onEntityUpdate` détruit une entité qui passe sous `Y=-64`.

À la hauteur vanilla maximale `Y=256`, la distance verticale vers l'ancre
`Y=-60` vaut `316` blocs. Même avec les 12 blocs maximum avant recentrage X/Z,
elle reste donc très inférieure à la portée du Dragon. Cette preuve retire
l'ambiguïté technique ; la matrice visuelle reste néanmoins obligatoire pour
valider le rendu exact des clients utilisés par Volkaria.

## Correctif retenu

En profil `AUTO` avec `ENDER_DRAGON` et `invisible_entity: true`, la position
est désormais :

```text
X = X du joueur au dernier ancrage
Y = -60, valeur absolue
Z = Z du joueur au dernier ancrage
```

Configuration :

```yaml
bossbar:
  entity_type: ENDER_DRAGON
  invisible_entity: true
  follow_player: true

  placement:
    profile: AUTO
    dragon_absolute_y: -60.0
    dragon_reanchor_distance: 12.0
```

`dragon_absolute_y` est borné entre `-62` et `-16`. La valeur par défaut
`-60` reste sous le monde 1.8 normal tout en gardant une marge au-dessus de la
limite de suppression client.

Les anciens paramètres `dragon_distance` et `dragon_vertical_offset` ne sont
plus utilisés par le profil Dragon `AUTO`. Si une ancienne configuration les
contient sans `dragon_absolute_y`, le plugin applique automatiquement `-60` en
mémoire et écrit une alerte de migration explicite au démarrage. Il n'existe
donc pas deux branches de placement concurrentes.

## Coût réseau et serveur

Le système reste packet-only : aucune entité Bukkit, aucune IA, aucun chunk
forcé et aucun parcours d'entités.

Deux réductions de trafic ont été ajoutées :

- le Dragon n'est recentré qu'après 12 blocs de déplacement au lieu d'envoyer
  une téléportation à chaque actualisation ;
- les métadonnées ne sont renvoyées que si la vie, le titre ou le drapeau
  d'invisibilité change réellement.

Un changement de monde invalide proprement l'ancien handle et recrée le faux
boss dans le nouveau monde du joueur.

## Tests automatisés

Les tests couvrent :

- le bornage de la hauteur absolue et la marge au-dessus de `Y=-64` ;
- la portée client calculée du Dragon, y compris à `Y=250` avec le recentrage
  X/Z au seuil maximal ;
- les hauteurs joueur `5`, `30`, `64`, `120` et `250` ;
- le seuil exact de recentrage ;
- la suppression des paquets de métadonnées identiques ;
- la détection des anciennes clés ;
- l'absence des deux anciennes clés dans le `hud.yml` livré.

Commande validée le 26 août 2026 :

```powershell
mvn test
```
