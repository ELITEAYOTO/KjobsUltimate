# KjobsUltimate V3.14 — Hot Path Performance

## Objectif

V3.14 optimise les chemins exécutés très fréquemment quand plusieurs centaines
de joueurs minent, récoltent, tuent des mobs ou gagnent de l'XP en même temps.

La priorité est de supprimer le travail inutile **sans changer le gameplay**.
Aucun accès Bukkit/NMS/PlaceholderAPI n'est déplacé sur un thread async.

## 1. Cooldowns de blocs

### Avant

Chaque bloc cassé construisait une String :

```text
world-uuid:x:y:z
```

puis la stockait dans une `Map<String, Long>` du `PlayerData`.

Les entrées expirées restaient dans la map tant que le joueur était connecté.

### V3.14

```text
BlockBreakEvent
    ↓
BlockCooldownService
    ↓
UUID joueur
    ↓
UUID monde
    ↓
position packée dans un long
    ↓
long -> expiry primitive map
```

Les avantages :

- aucune String de position dans le hot path ;
- expiration supprimée opportunistement ;
- cache borné par joueur ;
- cache entièrement RAM, séparé des données persistantes ;
- purge immédiate au quit.

Configuration :

```yaml
performance:
  hot_path:
    block_cooldowns:
      max_entries_per_player: 4096
      cleanup_every_checks: 128
```

`max_entries_per_player` est une limite de sécurité mémoire. Si elle est
atteinte, les expirations les plus proches sont évincées afin d'empêcher une
croissance RAM non bornée.

## 2. Slots de métiers

`isJobActive()` ne crée plus de `ArrayList`.

Avant :

```text
BlockBreak
  -> getActiveJobs()
  -> new ArrayList
  -> scan slots
  -> contains(job)
```

V3.14 :

```text
BlockBreak
  -> scan direct slots 1..N
  -> return dès que le job est trouvé
```

Les calculs `global level` et `highest active level` utilisent également les
slots directement.

## 3. Runtime config snapshot

Les options consultées sur chaque bloc/kill sont chargées une fois lors du
start ou `/kjobs reload` :

- Creative/Spectator ;
- Silk Touch ;
- crops mature only ;
- cooldown de bloc ;
- options canne/cactus ;
- daily cap enabled ;
- cooldown victime PvP ;
- nombre de slots.

Les listeners ne traversent donc plus `FileConfiguration` pour ces valeurs à
chaque événement.

## 4. Multiplicateurs XP

### Permissions

La section :

```yaml
xp_multipliers:
  permissions:
    kjobsultimate.xp.vip: 1.25
```

est compilée en règles RAM lors du reload.

Le meilleur multiplicateur du joueur est ensuite mis en cache :

```yaml
performance:
  hot_path:
    xp:
      permission_cache_ttl_ticks: 100
      permission_cache_max_players: 2048
```

Avec `100` ticks, un changement de permission est visible au plus tard environ
5 secondes plus tard sans reload/reconnexion.

Mettre `permission_cache_ttl_ticks: 0` désactive le TTL cache si nécessaire.

### Event multiplier

`xp_multipliers.event_multiplier` n'est plus relu à chaque gain XP.

```yaml
event_multiplier_refresh_ticks: 20
```

signifie une relecture maximum par seconde.

## 5. Daily XP

L'ancien chemin reconstruisait un `HashSet` avec tous les jobs à chaque gain.

V3.14 :

- le job courant est vérifié immédiatement ;
- le sweep complet des jobs n'existe que si le cap global est activé ;
- ce sweep est amorti avec `global_daily_sweep_interval_ticks`.

## 6. XP restant jusqu'au niveau max

La somme des XP restantes jusqu'au niveau maximum est pré-calculée dans chaque
`JobDefinition`.

Le hot path passe donc d'une boucle `niveau actuel -> niveau 50` à une lecture
O(1).

## 7. Mutation PlayerData groupée

Un gain XP normal mettait auparavant séparément à jour :

- daily XP ;
- niveau ;
- XP ;
- display job.

Chaque setter pouvait incrémenter la revision visible.

V3.14 utilise `applyJobXpGain()` et ne produit qu'une mutation/revision groupée
pour l'état final du gain.

## 8. Kgui invalidation queue

XP + quête pendant le même tick peuvent tous deux marquer le même joueur dirty.

V3.14 fusionne ces signaux :

```text
XP dirty ───┐
Quest dirty ├─> UUID joueur -> Pending invalidation -> 1 flush
Slot dirty ─┘
```

La revision globale des ContentProviders Kgui n'est incrémentée qu'une fois par
batch de flush.

```yaml
ui_invalidation:
  enabled: true
  flush_interval_ticks: 1
  max_players_per_flush: 250
```

Les caches JobsView/QuestView restent invalidés immédiatement pour garantir que
PlaceholderAPI/Ktab ne lise jamais un snapshot obsolète.

## 9. PvP Prétorien

Le tracking du dernier hit ne scanne plus toute la map à chaque coup.
Le nettoyage complet est amorti tous les 128 hits, tandis qu'un hit expiré est
rejeté lorsqu'il est consommé.

Les caches PvP du joueur sont aussi nettoyés au quit.

## 10. Pilleur

Le listener Pilleur passe lui aussi par `JobActionService` :

- XP ;
- money ;
- HUD ;
- quête

utilisent désormais la même unité.

Les crafts TNT/Dynamite utilisent `CraftUnitResolver`, y compris pour les
shift-clicks.

## 11. Base V2 propre

V3.14 ne conserve plus les anciennes compatibilités de configuration runtime :

- aucune permission `kjob.*` n’est déclarée dans `plugin.yml` ;
- pas de fallback `WHEAT` pour le bloc de blé : `CROPS` uniquement ;
- pas de fallback `anti_abuse.pvp_target_cooldown` ;
- pas de `pilleur.dynamite_nbt_example`.

Le NBT `sparrowmc-item` est volontairement conservé : il s'agit du contrat des
items custom existants, pas d'une compatibilité de configuration obsolète.

## Hors périmètre V3.14

La persistance de progression de quête fait encore une sauvegarde async par
mutation. Elle sera traitée en V3.15 avec un buffer/batch de writes.

Le HUD NMS et les métriques `/kjobs perf` restent prévus en V3.16.
